# weewx-livedata

Writes the current WeeWX readings to `live.json` on your web host, every few
seconds. It publishes only the latest snapshot and keeps no history; archive
reports are configured separately.

A WeeWX service collects LOOP readings and sends signed HTTP posts to
`live.php`. The PHP endpoint writes the file beside your pages. Your page reads
that static file, so visitors do not trigger PHP execution or database queries.
The station only needs an outgoing connection.

The project originated as
[hilman2/weewx-livedata](https://github.com/hilman2/weewx-livedata).

## Requirements

* A web host running PHP over HTTPS, with write access to the directory
  holding `live.php`.
* No Python package beyond WeeWX.

## Installation

Install `livedata` from the [WeeWX packages catalog](https://github.com/weewx-packages/catalog/blob/main/packages/livedata.md).
The catalog page lists the current release, its WeeWX and Python
requirements, and the install, update and removal commands.

The installer registers the posting service and the `LiveData` report. It
creates a signing key for a new station and keeps your existing settings and
key on an update.

Set the endpoint URL in `weewx.conf`:

``` ini
[StdRESTful]
    [[LiveData]]
        url = https://example.com/live.php
```

Restart WeeWX. The next report run generates `live.php` in the `[StdReport]`
`HTML_ROOT`, usually `public_html`, using the signing key in `weewx.conf`.
The FTP or rsync report uploads it with your pages. If you publish another way,
upload that generated copy yourself. After an update, publish the regenerated
endpoint the same way.

Open the endpoint URL in a browser. It should answer `POST only`. If you see PHP
source, configure the host to execute PHP before continuing.

Once LOOP packets arrive, `live.json` should appear beside
`live.php`. Your page can fetch it at `https://example.com/live.json`.

Uninstalling leaves the generated files in `HTML_ROOT` and on your web host.
Remove `live.php` and `live.json` there when you stop publishing live readings.

## Configuration

The smallest working configuration is the `url` shown under
[Installation](#installation). The installer writes the other options.

### Reading the live values

Read `live.json` with browser caching disabled:

``` js
const response = await fetch('live.json', {cache: 'no-store'});
if (!response.ok) throw new Error('Live readings: HTTP ' + response.status);
const live = await response.json();
console.log(live.current);
```

Repeat the request every ten seconds with the default `post_interval`.

`current` contains the latest value seen for each observation. Values are raw
numbers in the unit system identified by `usUnits`; your page converts and
formats them. Use `dateTime` to show the age of the readings. An observation
that has never reported or has gone stale is absent, so do not treat a missing
value as zero.

`day` contains today's minimum and maximum for the observations configured in
`extremes`.

The [live file format](docs/how-it-works.md#the-live-file)
describes the fields and unit-system codes.

### Options

These options go under `[StdRESTful] [[LiveData]]` in `weewx.conf`.

#### url

The URL of `live.php`. Required. The installer sets `replace_me`; the service
does not post until it is replaced.

#### secret

The shared signing key, generated by the installer. Required. The key itself is
never sent. To change it, edit `weewx.conf` and restart WeeWX. The next report
run regenerates `live.php`; publish the generated copy to your web host.

#### post_interval

Seconds between posts. Default is `10`. Every LOOP packet updates the readings
regardless of this interval.

#### extremes

Observations whose daily minimum and maximum are included in `day`. Default is
none. The installer sets `outTemp, windSpeed, windGust, barometer, rain`. Set
it empty to omit daily extremes:

``` ini
extremes =
```

#### data_binding

Database binding used to read daily extremes. Default is `wx_binding`.

#### log_success

Whether each successful post is logged. If it is not set here, it comes from
`[StdRESTful]` or the top of `weewx.conf`, and is `True` when neither sets it.
At the default interval that is one log line every ten seconds. Set
`log_success = False` to stop it.

#### log_failure

Whether a failed post is logged. Inherited like `log_success`, `True` when
nothing sets it.

#### Posting thread options

These options are passed to WeeWX's posting thread:

| Option | Default | Meaning |
| --- | --- | --- |
| `stale` | `60` | Seconds after which a queued snapshot is no longer posted. |
| `timeout` | `10` | Seconds to wait on the socket. |
| `max_tries` | `3` | Attempts per post. |
| `retry_wait` | `5` | Seconds between attempts. |
| `max_backlog` | `1` | Snapshots that may wait in the queue. |
| `skip_upload` | `False` | Prepare and sign each post without sending it. |

Any other key in this section is also passed to the posting thread. A key it
does not accept raises an error when WeeWX loads the service.

## Limitations

* The station and host clocks must be within 120 seconds for signed requests.
  An accepted upload returns HTTP 204.
* The endpoint keeps the last `live.json` when uploads stop, so pages must
  check `dateTime`. It does not provide history.
* Daily extremes from the database are not converted. LOOP and archive data
  should use the same unit system.

## Development

Run the tests with WeeWX's dependencies installed and its Python executable on
`PATH`. With a WeeWX checkout, also set `PYTHONPATH=/path/to/weewx/src`:

```sh
just fast
```

The endpoint tests run `live.php` under PHP's built-in HTTP server. They require
`php` on `PATH` and are skipped if it is missing.

[PUBLISHING.md](PUBLISHING.md) describes the release steps.
